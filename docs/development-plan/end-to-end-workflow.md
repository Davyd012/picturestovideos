## Delivery order and gates

1. **Contract:** define composition, timing, invalid-input policy, and legacy conversion. Add model tests before changing consumers.
2. **Integration:** make preview and renderer consume the same resolved composition. Complete clip-ID framing and preservation.
3. **Evidence:** build decoded-frame parity tests and correct differences. Do not label editing preview as export-accurate until this gate passes.
4. **Platform and reliability:** capability detection, localized errors, storage recovery, caching, cancellation, and cleanup.
5. **Experience:** review the guided flow, accessibility, localization, and responsive layouts against the integrated behavior.
6. **Release:** run automated suites, real-device and desktop checks, and review real videos. Record results and unresolved issues.

Each stage depends on the previous stage's contract; platform and storage investigation can proceed in parallel without changing that contract. A stage is complete only when its checkboxes and acceptance criteria pass.

## 5. Persistence, recovery, and rendering lifecycle

### Storage and migration

- [ ] Enumerate supported schema versions and create fixtures for each meaningful migration, including missing IDs, legacy captions that were intentionally displayed, missing settings, and unknown future schema versions. Assert both semantic results and stable IDs after a second save/reopen.
- [ ] Decide and document which legacy titles/taglines become captions. Preserve intentional visible captions without causing new projects to show accidental filenames.
- [x] Test actual repository save, replacement, reopen, and multiple-project isolation. IO repository tests cover these paths, malformed projects, one invalid project among valid projects, staged-write failures, interrupted saves, and recovery from a previous valid copy. A repeated-source project with distinct per-occurrence fit, crop, caption, motion, and transition settings is saved, reopened, saved again, and reopened again with IDs and settings preserved. Shared Preferences remains the non-IO fallback and has not been qualified for large or durable project collections.
- [ ] Design a durable IO save strategy with an explicit commit point, validation before replacement, recoverable previous data, and no silent data loss. The implementation has these stages and failure injection covers staging and backup rotation; every filesystem/provider failure mode and incompatible newer versions remain open.
- [ ] Test missing-file detection and relinking for image and audio sources, repeated occurrences, changed paths, inaccessible files, and changed file content. Preserve IDs and edits; show unresolved sources and let the user retry or select replacements.
- [ ] Make save, recovery, and relink states visible and localized. Preserve unsaved work on errors and tell users what they can do next.

### Render resources and lifecycle

- [x] Audit cache keys for source identity and content changes, clip timing, fit/crop, motion, transitions, captions, font, output size/frame rate, audio, renderer version, and relevant encoding options. Segment keys and rendered-preview signatures now include SHA-256 content fingerprints for image and audio sources; keys also cover timing, framing, motion, captions, template/transitions, font, output settings, renderer version, and encoder arguments. A same-path/same-size/same-timestamp image replacement test confirms the rendered signature and decoded output change. Hash reads check cancellation; changed inputs abort before a result is published. Cache pruning recognizes both legacy 16-character and current SHA-256 filenames.
- [x] Verify cache size bounds, pinning, concurrent renders, eviction, corrupt entries, and cleanup after startup/interruption. Do not delete user-owned inputs or final outputs. Tests cover byte bounds, pinning, paired media/checksum eviction, cancelled lock waiters, concurrent renders sharing one verified segment, corrupted segment regeneration, and stale interrupted directory/checksum cleanup at the next render start. Live leases and completed MP4 outputs are preserved. Cleanup uses a five-minute heartbeat grace period.
- [ ] Trace success, failure, cancellation, and disposal across all render phases. Stop child processes or native sessions, release handles and pins, remove partial outputs and temporary files, retain valid completed output, and prevent stale progress or results from replacing newer work.
- [x] Test cancellation before startup, during segment generation, composition, audio processing, and finalization; test repeated cancellation and restart. Verify progress is monotonic, bounded, phase-aware, and does not report success before output is finalized. Windows FFmpeg tests cover pre-start cancellation, segment-process cancellation, and cancellation during the renderer's combined audio/video finalization process; they assert temp cleanup, bounded monotonic progress, repeated cancellation, and successful restart. Physical TB310FU Android integration also cancelled an active native FFmpeg render in 153 ms and confirmed no partial render directory remained. Composition, audio processing, and mux finalization run in one FFmpeg process, so those internal stages are not independently cancellable. Other target platforms remain untested.
- [ ] Measure peak memory and disk use with large photos, many clips, long audio, repeated previews, and cancellation. Bound decoded image and process concurrency; record device, workload, peak, and acceptable budget before release.
- [ ] Test missing/unreadable sources, insufficient space, permission failures, FFmpeg failure, invalid output, and app interruption. Surface localized recovery actions and retain the editable project.

**Acceptance:** no tested interrupted/invalid save loses the last valid project; no tested render path leaks active processes, pins, or partial output; cache changes cannot return stale media.
